# انواع دیتابیس‌ها: OLTP در برابر OLAP؛ داده چطور ذخیره می‌شود؟

**جلسه یازدهم | مدرس: محمدصادق زاهدی | دوشنبه ۲۵ آبان ۱۴۰۵، ساعت ۲۰**

## هدف و نقشه جلسه

مدرس این جلسه را نخستین بخش از دو جلسه درباره **لایه ذخیره‌سازی (Storage Layer)** در چرخه مهندسی داده معرفی می‌کند. هدف جلسه حاضر، شناخت تفاوت بارکاری دیتابیس عملیاتی و تحلیلی، بررسی شیوه ذخیره‌سازی سطری و ستونی، آشنایی با فرمت‌های فایل و توضیح چگونگی جمع‌کردن سرعت خواندن و نوشتن است. جلسه بعد قرار است از همین مفاهیم برای بحث معماری‌های Data Warehouse و Data Lake استفاده کند.

مدرس در معرفی خود به حدود ۱۵ سال سابقه در حوزه داده، تجربه در تحلیل شبکه‌های اجتماعی و موتور جست‌وجو، تمرکز اخیر بر Data Engineering و پیشینه دانشگاهی در NLP اشاره می‌کند.

**پس از مطالعه این جلسه** باید بتوانیم بگوییم چرا Query تحلیلی می‌تواند دیتابیس عملیاتی را تحت فشار بگذارد، Parquet چه ساختاری دارد، تفاوت B-Tree و LSM چیست و خانواده MergeTree در ClickHouse چگونه با Part و Merge کار می‌کند.


## جایگاه Storage در چرخه مهندسی داده

در مرور مدرس، داده از سامانه‌های مبدأ مانند دیتابیس‌های عملیاتی، API، Excel، Web Scraping و سنسورها وارد یک پلتفرم داده می‌شود. گاهی انتقال دسته‌ای انجام می‌شود، گاهی با CDC و ابزارهایی مثل Kafka Connect تغییرات ثبت و منتقل می‌شوند. سپس پاک‌سازی، Join و تبدیل با ابزار مناسب انجام می‌شود و نتیجه از طریق داشبورد، Feature Store یا API در اختیار مصرف‌کننده قرار می‌گیرد.

```text
Source Systems → Ingestion / CDC → Transformation → Serving
       ↘              ↓                 ↓             ↙
                     Storage Layer
```

| خانواده سیستم | نمونه‌ای که در کلاس مطرح شد | هدف رایج |
|---|---|---|
| پایگاه داده عملیاتی | PostgreSQL، MySQL، Oracle | ثبت فعالیت برنامه |
| Document Database | MongoDB | سندهای با ساختار انعطاف‌پذیر |
| Cache / Key-Value | Redis | دسترسی سریع به داده |
| Graph Database | Neo4j | مدل‌کردن ارتباط‌های گرافی |
| Vector Database | نام ابزار خاصی ذکر نشد | جست‌وجوی تشابه برداری |
| Analytical Database | ClickHouse، Pinot، StarRocks | تحلیل حجم زیاد داده |

نکته مدرس این است که هر سازمان الزاماً به همه این فناوری‌ها نیاز ندارد. ابزارهای مورد نیاز را **نوع مسئله و بارکاری** تعیین می‌کند، نه فهرستی از فناوری‌های محبوب.

> **تکمیل فنی:** OLTP و OLAP در اصل *نوع بارکاری* هستند و نه دو رده کاملاً جدا و غیرقابل‌هم‌پوشانی از محصولات. بعضی موتورهای امروزی بارکاری ترکیبی یا HTAP را نیز پشتیبانی می‌کنند.

## OLTP در برابر OLAP: چرا دو نوع بارکاری داریم؟

مدرس مثال یک فروشگاه آنلاین را مطرح می‌کند. وقتی مشتری ثبت‌نام می‌کند، سفارش می‌دهد یا وضعیت پرداخت را بررسی می‌کند، سامانه به تراکنش‌های کوتاه و هم‌زمان پاسخ می‌دهد. این الگوی **Online Transaction Processing (OLTP)** است. وقتی مدیر می‌خواهد مجموع فروش پنج سال گذشته را به تفکیک شهر بداند، روی تعداد بسیار بیشتری رکورد محاسبه و تجمیع انجام می‌شود؛ این بارکاری **Online Analytical Processing (OLAP)** است.

| ویژگی | OLTP | OLAP |
|---|---|---|
| هدف غالب | اجرای فرایند کسب‌وکار | تحلیل و تصمیم‌گیری |
| پرسش نمونه | «وضعیت سفارش ۱۰۱ چیست؟» | «فروش پنج سال گذشته در هر شهر چقدر است؟» |
| تعداد ردیف در هر عملیات | معمولاً کم | ممکن است میلیون‌ها یا میلیاردها باشد |
| نوع عملیات | INSERT، UPDATE، جست‌وجوی نقطه‌ای | Scan، GROUP BY، Aggregation، JOIN |
| هم‌زمانی | تعداد زیادی تراکنش کوتاه | تعداد و اندازه Queryها تابع سامانه |
| ستون‌های موردنیاز | اغلب بخش قابل‌توجهی از رکورد | غالباً زیرمجموعه ستون‌ها |
| چیدمان متداول | سطری و ایندکس مناسب | اغلب ستونی و فشرده |
| نمونه فناوری | PostgreSQL، Oracle | ClickHouse، Pinot، StarRocks |

چرا Query تحلیلی را مستقیماً روی دیتابیس Production اجرا نکنیم؟ مدرس توضیح می‌دهد که اسکن‌های سنگین می‌توانند CPU، دیسک و منابع اشتراکی را اشغال کنند و زمان پاسخ تراکنش‌های کاربران را بالا ببرند. یک Read Replica فشار خواندن را از Primary کم می‌کند، اما لزوماً موتور سطری را به موتور تحلیلی تبدیل نمی‌کند. به همین دلیل انتقال داده با ETL یا CDC به لایه تحلیلی یک الگوی رایج است.

> **تکمیل فنی:** هیچ‌کدام از این دو گروه ذاتاً «همیشه سریع‌تر» نیستند. سرعت را نوع Query، ایندکس، اندازه داده، سخت‌افزار، طراحی Schema و میزان هم‌زمانی تعیین می‌کند. اجرای تحلیل روی Read Replica یا PostgreSQL با ایندکس و Partition مناسب در برخی ابعاد داده کاملاً قابل قبول است.

## ذخیره‌سازی سطری و ستونی

**نمای جدول** که کاربر با `SELECT` می‌بیند الزاماً چیدمان فیزیکی بایت‌ها روی دیسک نیست. در چیدمان سطری، مقادیر مربوط به یک رکورد نزدیک هم قرار می‌گیرند؛ در چیدمان ستونی، مقادیر یک ستون به‌شکل منظم کنار هم ذخیره می‌شوند.

```text
Logical table
ID | City   | Amount
 1 | Tehran | 120
 2 | Shiraz | 210
 3 | Tehran | 150

Row-oriented:    [1,Tehran,120] [2,Shiraz,210] [3,Tehran,150]
Column-oriented: [1,2,3] [Tehran,Shiraz,Tehran] [120,210,150]
```

اگر Query به دنبال تمام ویژگی‌های سفارش شماره ۳ باشد، طراحی سطری معمولاً دسترسی طبیعی‌تری به همه مقادیر یک ردیف دارد. اگر Query فقط `AVG(Amount)` یا `GROUP BY City` بخواهد، طراحی ستونی می‌تواند صرفاً Columnهای لازم را بخواند.

| نوع پرسش | چیدمان غالباً مناسب‌تر | دلیل |
|---|---|---|
| بازیابی رکورد با شناسه | سطری | کنار هم بودن فیلدهای یک رکورد |
| مجموع مبلغ روی کل تاریخچه | ستونی | خواندن فقط ستون مبلغ |
| گروه‌بندی شهر و مبلغ | ستونی | خواندن ستون‌های محدود |
| به‌روزرسانی کوتاه با تأخیر کم | سطری/طراحی تراکنشی | سازگاری با الگوی نوشتن |

مدرس برای توضیح هزینه خواندن، مثال ساده‌ای از تعداد Pageها و Blockها نشان می‌دهد. هدف مثال فهم الگوی دسترسی است، نه ارائه فرمول ثابت «یک Page در برابر پنج Page» برای تمام دیتابیس‌ها.

> **تکمیل فنی:** ذخیره‌سازی ستونی به‌تنهایی تضمین‌کننده Vectorization یا Data Skipping نیست. این قابلیت‌ها به موتور اجرا، طراحی Index، آمارهای ذخیره‌شده و Predicate بستگی دارند. همچنین Row Store می‌تواند Index ستونی یا قابلیت‌های تحلیلی دیگری داشته باشد.

### چرا ذخیره‌سازی ستونی برای تحلیل جذاب است؟

مدرس چهار مزیت را برجسته می‌کند: **Column Pruning** برای خواندن ستون‌های لازم؛ **Encoding و Compression** بهتر به‌خاطر یکسان بودن نوع مقادیر یک ستون؛ **پردازش برداری** روی مجموعه‌ای از مقادیر؛ و **Data Skipping** با کمک آماری مانند Min/Max.

برای نمونه، اگر میلیون‌ها مقدار در ستون شهر فقط از تعداد محدودی نام تشکیل شده باشد، Dictionary Encoding می‌تواند به‌جای تکرار متن شهرها، شناسه کوچک نگه دارد. اگر مقادیر یکسان متوالی باشند، Run-Length Encoding یا RLE تعداد تکرار را ثبت می‌کند.

> **مثال اضافی:** در ستونی با داده‌های `Tehran, Tehran, Tehran, Shiraz` می‌توان دیکشنری `Tehran=0` و `Shiraz=1` ساخت و دنباله شناسه‌ها را به صورت `0×3, 1×1` نمایش داد. این یک مدل مفهومی است؛ نسبت فشرده‌سازی واقعی به داده و Encoding انتخابی وابسته است.

## Data Format: متن در برابر باینری، سطری در برابر ستونی

مدرس به تفاوت فرمت ذخیره‌سازی فایل و موتور پایگاه داده می‌پردازد. یک دیتابیس تحلیلی ممکن است فرمت داخلی اختصاصی داشته باشد، اما در Data Pipeline فایل‌هایی نظیر JSON، Avro، Protobuf و Parquet هم انتقال یا نگهداری می‌شوند.

| فرمت | شکل غالب | Schema | کاربرد رایج |
|---|---|---|---|
| JSON | متن، رکورد/سندمحور | نام فیلدها داخل سند | API و Log |
| Avro Object Container | باینری، رکوردگرا | Schema در Header فایل | انتقال و نگهداری رکوردها |
| Protobuf | باینری، پیام‌محور | قرارداد `proto` در دو سمت | gRPC و ارتباط سرویس‌ها |
| Parquet | باینری، ستونی | Schema و Metadata در Footer | Data Lake و تحلیل |

### JSON

در JSON کلیدهایی مثل `id` و `city` ممکن است در هر رکورد تکرار شوند و اعداد نیز هنگام Encoding متنی به کاراکتر تبدیل شوند. مزیت آن خوانایی و سازگاری گسترده است. مدرس از یک مثال نمایشی با اختلاف چشمگیر حجم JSON و باینری یاد می‌کند.

> **تکمیل فنی:** JSON از نظر *ساختار داده* فاقد نوع نیست؛ نوع‌های Number، String، Boolean، Null، Array و Object دارد. اما نمایش آن متنی است و عدد هنگام Serialize به بایت‌های متن تبدیل می‌شود. فشرده‌سازی مانند gzip هم می‌تواند بخشی از سربار JSON را کاهش دهد.

### Avro و Schema Registry

در فایل Avro Object Container، Schema در Header ذخیره می‌شود و داده‌ها به‌صورت باینری Encoding می‌شوند؛ بنابراین نام فیلد لازم نیست برای هر مقدار دوباره نوشته شود. مدرس سپس کاربرد رایج Schema Registry در Kafka را توضیح می‌دهد: به‌جای ارسال Schema در تک‌تک پیام‌ها، فرستنده از Schema ثبت‌شده و شناسه آن استفاده می‌کند و مصرف‌کننده قرارداد را برمی‌دارد.

> **تکمیل فنی:** وجود Schema ID داخل پیام Kafka جزو خودِ استاندارد عمومی Avro نیست؛ این یک قرارداد Wire Format در سامانه‌هایی مثل Confluent Schema Registry است. همچنین Kafka الزامی ندارد که هر پیام فقط یک رکورد Avro باشد.

### Protocol Buffers

در Protobuf قرارداد فیلدها در فایل `.proto` تعریف می‌شود. Wire Format با شماره فیلد و Wire Type امکان تشخیص اجزای پیام را می‌دهد؛ مولد کد `protoc` می‌تواند بر اساس قرارداد، کد لازم را برای زبان‌های مختلف تولید کند. مدرس کاربرد Protobuf را به‌ویژه در ارتباط‌های gRPC مطرح می‌کند.

> **تکمیل فنی:** Wire Type به‌تنهایی «تعداد بایت بعدی» را همیشه مشخص نمی‌کند. بعضی فیلدها Varint هستند و برخی Length-Delimited که طول جداگانه دارند. حذف یا تغییر شماره فیلد هم باید با قواعد سازگاری Schema انجام شود و صرفاً نبودن Tag، علت حذف فیلد را به خواننده اطلاع نمی‌دهد.

## ساختار داخلی Parquet

Parquet برای تحلیل ستونی طراحی شده است. مدرس معماری آن را به ترتیب **Row Group → Column Chunk → Page** توضیح می‌دهد و نقش **Footer** را برجسته می‌کند.

```text
Parquet file
├── Row Group 0
│   ├── Column Chunk: City
│   │   ├── Page 0
│   │   └── Page 1
│   └── Column Chunk: Amount
│       └── Page 0
├── Row Group 1
│   ├── Column Chunk: City
│   └── Column Chunk: Amount
└── Footer: schema, offsets, statistics, row-group metadata
```

- **Row Group:** مجموعه‌ای از ردیف‌ها که در فایل به گروه‌هایی تقسیم می‌شوند؛ اندازه گروه بر عملکرد خواندن، حافظه و موازی‌سازی اثر دارد.
- **Column Chunk:** داده یک ستون درون یک Row Group.
- **Page:** واحد داخلی Encoding و Compression در Column Chunk.
- **Footer:** Metadata فایل، شامل Schema، محل Column Chunkها و آمار در صورت وجود.

مدرس مزیت‌های Parquet را Column Pruning، Encoding، Compression و Data Skipping معرفی می‌کند. برای مثال، اگر آمار یک Row Group نشان دهد `Amount` در بازه ۱۰ تا ۴۵۰ است، موتور خواننده ممکن است برای شرط `Amount > 900` آن گروه را بدون خواندن داده‌هایش کنار بگذارد.

> **تکمیل فنی:** Row Group با پارتیشن پوشه‌ای Data Lake یکسان نیست؛ Row Group ساختار داخلی یک فایل Parquet است. آمار Min/Max در همه فایل‌ها و برای همه ستون‌ها الزاماً موجود یا قابل استفاده نیست. اسکیپ‌کردن نیز به پشتیبانی Reader و شکل Predicate بستگی دارد.


## چالش نوشتن: چرا سرعت خواندن با هزینه نوشتن گره می‌خورد؟

اگر داده ستونی، فشرده و بر اساس کلید خاصی مرتب شده باشد، درج یک مقدار تازه در وسط داده از نظر مفهومی ممکن است به بازآرایی و بازفشرده‌سازی نیاز داشته باشد. مدرس با مثال درج نام شهر در دنباله فشرده‌شده نشان می‌دهد که انجام این عملیات برای تک‌تک رکوردهای ورودی می‌تواند هزینه‌بر شود. بنابراین طراحی سیستم باید بین *بهینه‌بودن خواندن* و *نوشتن با نرخ بالا* تعادل ایجاد کند.

> **تکمیل فنی:** «مرتب‌سازی همیشه لازم است» درست نیست؛ Data Skipping می‌تواند با آمارِ بخش‌های نامرتب هم رخ دهد، هرچند مرتب‌سازی روی کلید مناسب غالباً اثربخشی آن را بیشتر می‌کند. هزینه درج نیز به طراحی موتور و ساختارهای کمکی بستگی دارد.

## B-Tree و B+Tree

مدرس B-Tree را به دفترچه تلفن تشبیه می‌کند: کلیدها در یک درخت متوازن نگهداری می‌شوند و برای رسیدن به رکورد مناسب نیازی به جست‌وجوی تمام صفحه‌ها نیست. در B+Tree، داده یا اشاره‌گرهای رکورد معمولاً در سطح برگ قرار می‌گیرند و برگ‌ها برای پیمایش بازه‌ها می‌توانند به هم متصل باشند.

```text
          [30 | 60]
         /    |    \
   [<30]   [30..59]  [>=60]
```

در مثال مدرس، درج مقدار ۴۳ با پیمایش شاخه مناسب انجام می‌شود. این ساختار برای دسترسی نقطه‌ای و بازه‌ای بسیار مؤثر است.

> **تکمیل فنی:** در B-Tree ممکن است درج باعث Split یا تغییر چند Page شود، اما لزوماً «مرتب‌سازی کل داده روی دیسک» انجام نمی‌شود. همین‌طور یک موتور OLAP الزاماً از B-Tree بی‌بهره نیست و یک موتور OLTP هم می‌تواند از LSM استفاده کند.

## LSM Tree: ثبت سریع، ادغام در پس‌زمینه

در **Log-Structured Merge-Tree** ایده اصلی این است که نوشتن‌های جدید ابتدا به ساختار حافظه‌ای (Memtable) وارد شوند و در پیاده‌سازی‌های دارای ماندگاری، **Write-Ahead Log یا WAL** برای بازیابی پس از خرابی ثبت شود. وقتی Memtable به آستانه معین رسید، به فایل مرتب روی دیسک مانند SSTable تبدیل می‌شود. سپس Compaction در پس‌زمینه، فایل‌های مختلف را با سیاست مشخص ترکیب می‌کند.

```text
Write → WAL (durability)
     → Memtable (memory)
            ↓ flush
        SSTable L0
            ↓ background compaction
        SSTable L1 / L2 / ...
```

مدرس Tombstone را هم معرفی می‌کند: به‌جای حذف فیزیکی فوری تمام نسخه‌های یک کلید در فایل‌های قدیمی، نشانه‌ای برای حذف نوشته می‌شود و هنگام خواندن/Compaction در نظر گرفته می‌شود. Update نیز در بسیاری از LSMها به ثبت نسخه جدید متکی است.

| موضوع | B-Tree / B+Tree | LSM Tree |
|---|---|---|
| نوشتن | تغییر ساختار مرتب در Pageهای مرتبط | ورود به Memtable و Flush بعدی |
| خواندن | پیمایش شاخه‌های Index | بررسی لایه حافظه و فایل‌های سطح‌های مختلف |
| هزینه پس‌زمینه | نگهداری Page و Split | Compaction و بازنویسی فایل‌ها |
| Trade-off | Random Write و Page Management | Write Amplification، Read Amplification و Compaction |

مدرس به Bloom Filter اشاره می‌کند؛ ساختاری احتمالی که می‌تواند بگوید یک کلید **قطعاً در مجموعه نیست** یا **ممکن است باشد** و برای کاهش خواندن فایل‌های نامرتبط کاربرد دارد.

> **تکمیل فنی:** Bloom Filter در حالت استاندارد *منفی کاذب ندارد* ولی ممکن است مثبت کاذب بدهد؛ بنابراین وجود کلید را با قطعیت تأیید نمی‌کند. همچنین داشتن WAL به طراحی و تنظیمات موتور بستگی دارد و «نوشتن در Memtable» به‌تنهایی تضمین ماندگاری پس از Crash نیست.

> **تکمیل فنی:** RocksDB یک موتور **Embedded Key-Value** مبتنی بر LSM است، نه یک دیتابیس تحلیلی ستونی اختصاصی. همچنین LSM یک ایده عمومی برای طراحی ذخیره‌سازی است؛ مساوی دانستن همه موتورهای OLAP با LSM درست نیست.

## ClickHouse و خانواده MergeTree

مدرس در پایان، ClickHouse را به‌عنوان نمونه‌ای از ذخیره‌سازی تحلیلی معرفی می‌کند. در خانواده MergeTree، داده با Insert معمولاً به **Data Part**های جدید نوشته می‌شود. داده‌های هر Part بر اساس `ORDER BY` مرتب هستند و در پس‌زمینه برخی Partهای یک Partition با هم Merge می‌شوند.

```text
Insert batch A → Part A ┐
                        ├→ background merge → larger sorted Part
Insert batch B → Part B ┘
            ↘ sparse primary index / granules
```

یک مفهوم مهم **Granule** است: Index اولیه ClickHouse معمولاً Sparse است و به‌جای داشتن ورودی برای هر ردیف، برای بازه‌هایی از ردیف‌ها Mark نگه می‌دارد. مقدار رایج `index_granularity` برابر **۸۱۹۲ ردیف** است؛ عدد ۸۹۲ در متن پیاده‌سازی‌شده خطای انتقال گفتار است.

> **تکمیل فنی:** `index_granularity=8192` مقدار رایج پیش‌فرض است، نه اندازه ثابت همه Granuleها در همه تنظیمات. خانواده MergeTree از مفهوم Part و Background Merge بهره می‌گیرد، اما پیاده‌سازی آن همان LSM استانداردِ Memtable/SSTable نیست.

### ReplacingMergeTree

مدرس سناریوی ثبت چند نسخه از یک سفارش با `order_id` یکسان را مطرح می‌کند. در `ReplacingMergeTree` می‌توان نسخه‌های تازه را Insert کرد و هنگام Merge، رکوردهای هم‌کلید بر اساس Sort Key و ستون Version مدیریت می‌شوند.

> **تکمیل فنی:** Deduplication در `ReplacingMergeTree` **تدریجی و وابسته به Merge** است؛ فوراً تضمین نمی‌شود. برای نتیجه صحیح پیش از تکمیل Merge ممکن است Query با `FINAL` یا الگوی محاسباتی مناسب لازم باشد. شرط تشخیص رکورد تکراری، کلید مرتب‌سازی (`ORDER BY`) است، نه الزاماً نام ستونی مثل `order_id`.

### SummingMergeTree

در مثال دیگر، موتور `SummingMergeTree` می‌تواند مقادیر عددی ردیف‌هایی با کلید مرتب‌سازی مشترک را طی Merge با هم جمع کند و برای برخی جدول‌های تجمیعی مناسب است.

> **تکمیل فنی:** نتیجه تجمیع در `SummingMergeTree` نیز لزوماً بلافاصله پس از Insert نهایی نیست. برای Queryهای دقیق معمولاً باید Aggregation مناسب را در زمان خواندن رعایت کرد؛ انتخاب ستون‌های قابل‌جمع و کلید مرتب‌سازی برای صحت نتیجه حیاتی است.

### چرا Batch Insert توصیه می‌شود؟

مدرس توصیه می‌کند نوشتن در سامانه‌های تحلیلی به‌جای هزاران Insert تک‌ردیفی، در دسته‌های مناسب انجام شود؛ چون ایجاد Partهای بسیار کوچک فشار Merge و منابع را افزایش می‌دهد. در عین حال اندازه Batch باید با محدودیت حافظه، تاخیر مورد نیاز و تنظیمات موتور سنجیده شود.

> **تکمیل فنی:** «هرچه Batch بزرگ‌تر، بهتر» قاعده مطلق نیست. Batch بیش‌ازحد بزرگ می‌تواند Memory Spike، Retry پرهزینه یا تأخیر زیاد ایجاد کند. این تنظیم باید با داده واقعی Benchmark شود.

## مثال آموزشی: انتخاب ذخیره‌سازی برای یک فروشگاه

> **مثال اضافی:** سامانه سفارش آنلاین می‌تواند تراکنش‌های ثبت و پرداخت را در PostgreSQL مدیریت کند، تغییرات لازم را با CDC به یک Pipeline منتقل کند و گزارش فروش شهرها را در ClickHouse بسازد. داده‌های تاریخی حجیم نیز ممکن است در Parquet روی Object Storage نگهداری شوند. این یک معماری نمونه است، نه معماری نقل‌شده از سازمان‌های نام‌برده در کلاس.

| پرسش طراحی | گزینه‌ای برای ارزیابی | نکته تصمیم‌گیری |
|---|---|---|
| تراکنش پرداخت با قیود قوی | OLTP | صحت، Transaction و Concurrency |
| فروش چندساله به تفکیک شهر | OLAP | Scan و Aggregate و ظرفیت پاسخگویی |
| نگهداری فایل تاریخی | Parquet | Column Pruning و سازگاری ابزارها |
| انتقال تغییرات روزانه | CDC یا Batch | تازگی، هزینه و Recoverability |
| اصلاح سفارش در موتور تحلیلی | ReplacingMergeTree یا مدل جایگزین | نیاز به Deduplication قطعی هنگام Query |

## خلاصه مرور سریع

۱. OLTP برای اجرای تراکنش‌های کوتاه کسب‌وکار طراحی می‌شود و OLAP برای تحلیل مجموعه بزرگ داده.

۲. انتقال بار تحلیلی از Primary عملیاتی می‌تواند ریسک فشار به سرویس کاربران را کم کند؛ اما موتور تحلیلی خودکار در همه مقیاس‌ها لازم نیست.

۳. Row Store برای عملیات نقطه‌ای و Column Store برای خواندن چند ستون از تعداد ردیف بالا معمولاً مناسب‌تر است.

۴. Parquet یک فرمت ستونی فایل با ساختار Row Group، Column Chunk، Page و Footer است.

۵. B-Tree ساختار متوازن Index است؛ LSM نوشتن را به Memtable و Flush/Compaction تقسیم می‌کند.

۶. MergeTree در ClickHouse با Part، Sort Key و Sparse Index کار می‌کند؛ این ساختار مشابه بعضی ایده‌های LSM است، نه عین آن.

۷. ReplacingMergeTree و SummingMergeTree تا پیش از Merge ممکن است به منطق Query صحیح نیاز داشته باشند.

## سؤال‌های مرور و پاسخ کوتاه

۱. **چرا OLAP لزوماً جای OLTP را نمی‌گیرد؟** چون نیازهای تراکنش کوتاه، هم‌زمانی و تحلیل حجیم متفاوت‌اند.

۲. **چه خطر مهمی اجرای Query تحلیلی روی Primary دارد؟** مصرف منابع و افزایش Latency تراکنش‌های کاربران.

۳. **چرا چیدمان ستونی به Aggregate کمک می‌کند؟** فقط ستون‌های لازم خوانده می‌شوند و Encoding کارآمدتر می‌شود.

۴. **آیا Column Store همیشه از Row Store سریع‌تر است؟** خیر، به Query و طراحی موتور بستگی دارد.

۵. **فرق JSON و Avro در مثال کلاس چیست؟** JSON نمایش متنی با تکرار کلیدها دارد؛ Avro رکوردهای باینری و قرارداد Schema دارد.

۶. **Schema Registry چه فایده‌ای دارد؟** مدیریت Schema و ارجاع به نسخه/شناسه آن در پیام‌ها.

۷. **در Protobuf شماره فیلد چه کاربردی دارد؟** شناسایی فیلد مستقل از جایگاه فیزیکی آن.

۸. **ساختار اصلی Parquet چیست؟** Row Group شامل Column Chunk و Page؛ Footer شامل Metadata.

۹. **Data Skipping چه زمانی ممکن است؟** وقتی Reader از آمار مناسب و Predicate قابل استفاده برخوردار باشد.

۱۰. **مزیت B-Tree چیست؟** دسترسی نقطه‌ای و بازه‌ای بدون اسکن کامل درخت.

۱۱. **مزیت اصلی Memtable در LSM چیست؟** پذیرش نوشتن سریع و انتقال مرتب به SSTable در مرحله بعد.

۱۲. **WAL چه مشکلی را هدف می‌گیرد؟** بازیابی نوشتن‌ها پس از خرابی فرایند یا ماشین.

۱۳. **Bloom Filter چه چیزی را با قطعیت می‌گوید؟** نبودن عضو را، نه بودن آن را.

۱۴. **چرا ReplacingMergeTree بلافاصله تضمین یکتایی نمی‌دهد؟** چون حذف نسخه‌های تکراری طی Mergeهای پس‌زمینه انجام می‌شود.

۱۵. **چرا Insertهای بسیار کوچک در ClickHouse مسئله‌سازند؟** تولید تعداد زیادی Part کوچک و فشار روی Merge.
